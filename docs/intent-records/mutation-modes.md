title: Object mutation modes
date: 2026/09/10
source: @ottojung
kind: requirement

Object mutation mode at creation: capability-write or public-write. Default capability-write. For capability-write creation, the server returns a fresh high-entropy write capability once; subsequent put/delete require it. The capability is bearer authority, not user identity. It must not be obtainable through get and should be stored server-side only as a safe verifier/hash, not plaintext if simple to do. Public-write may be modified/deleted by anyone who knows namespace/key. No mode may make an object permanently undeletable, because undeletable storage grows without bound and forces namespace-level cleanup instead of ordinary object lifecycle. A request naming a removed mode is rejected explicitly, never downgraded into another mode. Content-addressed and crash-safe designs use public-write or capability-write with the address in the key. Objects created under a since-removed mode stay readable and deletable so their storage can be reclaimed, and they are treated as writable in place: a holder of delete permission on such an object can replace it by deleting it and creating the key again, and delete permission is not restricted to the creator. No server-enforced write-once property survives the removal of a mode, for new or pre-existing objects. Migrating a legacy on-disk layout must not be a promotion to a stronger access level: an existing `immutable` entry is legacy metadata and is migrated as itself, and an unrecognised or absent legacy mode becomes a writable mode rather than a mode that refuses writes. There is no migration of existing stored objects. Do not build roles/accounts/auth around this. If a simple mode-change API makes implementation significantly larger, omit it from v1 and specify mode as fixed for object lifetime.
